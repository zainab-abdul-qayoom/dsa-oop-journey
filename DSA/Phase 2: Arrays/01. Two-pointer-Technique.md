# Two-Pointer Technique — Complete Notes (All 3 Examples, Line-by-Line)

---

## 1. What is the Two-Pointer Technique? (Simplest Explanation)

Instead of using **one index** to walk through an array (often needing a nested loop to compare every element against every other — slow, O(n²)), you use **two index variables ("pointers")** moving through the array at the same time. This lets you compare, combine, or rearrange elements in a single pass — usually O(n).

```java
int left = 0;
int right = arr.length - 1;

while (left < right) {
    // do something with arr[left] and arr[right]
    left++;
    right--;
}
```

---

## 2. The Two Main Variations

### Variation A — Opposite Ends (converging pointers)
One pointer starts at index 0, the other at the last index. They move toward each other.
**Used for:** sorted arrays, pair-sum problems, palindrome checks, "max area" problems.

### Variation B — Same Direction (fast/slow pointers)
Both pointers start near the beginning, moving at different speeds, or one only advances when a condition is met.
**Used for:** removing/overwriting elements in-place, cycle detection (later, in Linked Lists).

**How to tell which one you need:** sorted array + looking for a pair/combination → Variation A. Modifying the array in-place, one direction only → Variation B.

---

## 3. How to Recognize a Two-Pointer Problem (Signal Words)

- "sorted array" + "find a pair/triplet that..." → Variation A
- "in-place" + "remove/move elements" → Variation B
- "palindrome" → Variation A (compare from both ends)
- "container", "area", "maximum width between two points" → Variation A
- Anything brute-forceable with a **nested loop comparing pairs** — ask "can I avoid the inner loop by moving pointers smartly instead?"

# EXAMPLE 1 — Move Zeroes (Variation B: same direction)

**Problem:** Move all zeroes in an array to the end, keep other elements in relative order, in-place.

```java
public void moveZeroes(int[] nums) {
    int slow = 0;
    for (int fast = 0; fast < nums.length; fast++) {
        if (nums[fast] != 0) {
            int temp = nums[slow];
            nums[slow] = nums[fast];
            nums[fast] = temp;
            slow++;
        }
    }
}
```

## Line-by-Line

**`int slow = 0;`** — `slow` tracks the position where the **next non-zero element should go**. It only moves forward when we actually place a non-zero value there.

**`for (int fast = 0; fast < nums.length; fast++)`** — `fast` scans through every element of the array, one at a time, from start to end.

**`if (nums[fast] != 0)`** — We only act when the current element is non-zero. Zeroes are simply skipped over by `fast` — they'll naturally end up at the back once everything else has been moved forward.

**`int temp = nums[slow]; nums[slow] = nums[fast]; nums[fast] = temp;`** — A standard swap: the value at `slow` and the value at `fast` trade places. This pushes the non-zero value found at `fast` back to the earliest available "non-zero slot" (`slow`), while whatever was sitting at `slow` (usually a zero, or already-placed value) moves out to where `fast` currently is.

**`slow++;`** — Since we just placed a non-zero value at `slow`, the *next* available slot for a non-zero value is one position ahead.

## Full Dry Run: `[0, 1, 0, 3, 12]`

| fast | nums[fast] | action | array after | slow |
|---|---|---|---|---|
| 0 | 0 | skip | `[0,1,0,3,12]` | 0 |
| 1 | 1 | swap(slow=0, fast=1) | `[1,0,0,3,12]` | 1 |
| 2 | 0 | skip | `[1,0,0,3,12]` | 1 |
| 3 | 3 | swap(slow=1, fast=3) | `[1,3,0,0,12]` | 2 |
| 4 | 12 | swap(slow=2, fast=4) | `[1,3,12,0,0]` | 3 |

**Final result:** `[1, 3, 12, 0, 0]` ✅

# EXAMPLE 2 — Container With Most Water (Variation A: opposite ends)

**Problem:** Given heights of vertical lines, find two lines that, with the x-axis, form the container holding the most water.

```java
public int maxArea(int[] height) {
    int left = 0, right = height.length - 1;
    int max = 0;

    while (left < right) {
        int smallestHeight = Math.min(height[left], height[right]);
        int width = right - left;
        int area = smallestHeight * width;

        if (area > max) {
            max = area;
        }

        if (height[left] < height[right]) {
            left++;
        } else {
            right--;
        }
    }
    return max;
}
```

## Line-by-Line

**`int left = 0, right = height.length - 1;`** — Start with the **widest possible container**: leftmost and rightmost poles.

**`int max = 0;`** — Tracks the best (largest) area seen so far across all pairs we check.

**`while (left < right)`** — Keep going until the two pointers meet or cross. Once they meet, there's no container left to form (needs two *different* poles).

**`int smallestHeight = Math.min(height[left], height[right]);`** — Water can never rise above the **shorter** of the two poles — it would spill over that side. So the shorter pole's height is the actual water level.

**`int width = right - left;`** — The distance between the two poles' **positions** (indices) — this is the container's width. Note: this is about *index positions*, completely separate from the height values.

**`int area = smallestHeight * width;`** — Water held = height × width, same as area of a rectangle.

**`if (area > max) { max = area; }`** — If this pair's area beats everything seen so far, it becomes the new best.

**`if (height[left] < height[right]) { left++; } else { right--; }`** — The key decision: **move the pointer at the shorter height, inward.** Why? The shorter pole is the bottleneck limiting the water level. Moving the *taller* pointer inward can only shrink the width while the height limit stays the same (or gets worse) — it can never improve the answer. Moving the *shorter* pointer inward is the only move with any chance of finding a taller pole and increasing the water level.

## Full Dry Run: `[1, 8, 6, 2, 5, 4, 8, 3, 7]`

| left | right | height[left] | height[right] | smallestHeight | width | area | max | move |
|---|---|---|---|---|---|---|---|---|
| 0 | 8 | 1 | 7 | 1 | 8 | 8 | 8 | left++ (1<7) |
| 1 | 8 | 8 | 7 | 7 | 7 | **49** | **49** | right-- (8 not<7) |
| 1 | 7 | 8 | 3 | 3 | 6 | 18 | 49 | right-- |
| 1 | 6 | 8 | 8 | 8 | 5 | 40 | 49 | right-- (8 not<8) |
| 1 | 5 | 8 | 4 | 4 | 4 | 16 | 49 | right-- |
| 1 | 4 | 8 | 5 | 5 | 3 | 15 | 49 | right-- |
| 1 | 3 | 8 | 2 | 2 | 2 | 4 | 49 | right-- |
| 1 | 2 | 8 | 6 | 6 | 1 | 6 | 49 | right-- |
| loop ends (left < right fails) | | | | | | | | |

**Final result:** `49` ✅ — found in the very second comparison, then confirmed as the best across every remaining pair.

# EXAMPLE 3 — 3Sum (Variation A + an outer loop)

**Problem:** Find all unique triplets (three different positions) in the array that sum to zero. No duplicate value-combinations in the result.

```java
class Solution {
    public List<List<Integer>> threeSum(int[] nums) {
        Arrays.sort(nums);
        List<List<Integer>> result = new ArrayList<>();

        for (int i = 0; i < nums.length; i++) {
            if (i > 0 && nums[i] == nums[i - 1]) {
                continue;
            }

            int left = i + 1;
            int right = nums.length - 1;

            while (left < right) {
                int sum = nums[i] + nums[left] + nums[right];

                if (sum == 0) {
                    result.add(List.of(nums[i], nums[left], nums[right]));
                    left++;
                    right--;

                    while (left < right && nums[left] == nums[left - 1]) {
                        left++;
                    }
                    while (left < right && nums[right] == nums[right + 1]) {
                        right--;
                    }
                } else if (sum < 0) {
                    left++;
                } else {
                    right--;
                }
            }
        }
        return result;
    }
}
```

## Line-by-Line

**`Arrays.sort(nums);`** — Sorting first is what makes the whole approach work. Once sorted, moving `left` forward always increases the sum (bigger values going right), and moving `right` backward always decreases it — a reliable, predictable rule.

**`List<List<Integer>> result = new ArrayList<>();`** — Holds every valid triplet found, each as its own small list of 3 numbers.

**`for (int i = 0; i < nums.length; i++)`** — The **outer loop** fixes one number at a time as "the first number of the triplet." For each fixed `i`, two pointers search the rest of the array for a pair that sums with it to zero.

**`if (i > 0 && nums[i] == nums[i - 1]) { continue; }`** — Skips duplicate values for `i`. If this value is the same as the previous one, every triplet starting with it was already found in the previous iteration — skip to avoid duplicate work and duplicate results. The `i > 0` check avoids looking at `nums[-1]`, which doesn't exist.

**`int left = i + 1; int right = nums.length - 1;`** — Sets up two pointers in the **remaining part of the array**, right after the fixed `i`.

**`while (left < right)`** — Same boundary rule as before: stop once the pointers meet or cross.

**`int sum = nums[i] + nums[left] + nums[right];`** — The current triplet candidate's total.

**`if (sum == 0) { ... }`** — Found a valid triplet — save it, but there's cleanup needed before moving on (see below).

**`else if (sum < 0) { left++; }`** — Sum too small. Since the array is sorted, moving `left` forward picks a larger value, increasing the sum toward zero.

**`else { right--; }`** — Sum too big. Moving `right` backward picks a smaller value, decreasing the sum toward zero.

**Inside the `sum == 0` block:**

**`result.add(List.of(nums[i], nums[left], nums[right]));`** — Save the triplet.

**`left++; right--;`** — Move both pointers inward — reusing the same values again with the same `i` would just rediscover the same triplet.

**`while (left < right && nums[left] == nums[left - 1]) { left++; }`** — After moving, check: is the new `left` value the same as the one just used? If yes, using it again would produce an identical triplet — skip forward past all repeats of that value.

**`while (left < right && nums[right] == nums[right + 1]) { right--; }`** — Same idea for `right`, but compared against `nums[right + 1]` (the value just moved away from), since `right` moves backward instead of forward.

## Full Dry Run: `[-1, 0, 1, 2, -1, -4]`

**After sorting:** `[-4, -1, -1, 0, 1, 2]`
```
Index:   0   1   2   3  4  5
Value:  -4  -1  -1   0  1  2
```

**i = 0 (nums[i] = -4):**
| left | right | sum | decision |
|---|---|---|---|
| 1(-1) | 5(2) | -4-1+2=-3 | too small → left++ |
| 2(-1) | 5(2) | -4-1+2=-3 | too small → left++ |
| 3(0) | 5(2) | -4+0+2=-2 | too small → left++ |
| 4(1) | 5(2) | -4+1+2=-1 | too small → left++ |
| 5 | 5 | loop ends (left < right fails) | |

**i = 1 (nums[i] = -1):**
| left | right | sum | decision |
|---|---|---|---|
| 2(-1) | 5(2) | -1-1+2=0 ✅ | save `[-1,-1,2]` → left=3, right=4. No dup skips triggered. |
| 3(0) | 4(1) | -1+0+1=0 ✅ | save `[-1,0,1]` → left=4, right=3 → loop ends |

**i = 2 (nums[i] = -1):** same value as `nums[1]` → **skip** (duplicate `i`)

**i = 3 (nums[i] = 0):**
| left | right | sum | decision |
|---|---|---|---|
| 4(1) | 5(2) | 0+1+2=3 | too big → right-- |
| 4 | 4 | loop ends | |

**i = 4, i = 5:** not enough room for `left`/`right` → loop ends immediately.

**Final result:** `[[-1,-1,2], [-1,0,1]]` ✅ — matches expected output, no duplicates.

## 4. The General Template (Use This When Stuck)

1. **Is the array sorted (or can I sort it)?** If yes → likely Variation A.
2. **What does moving `left` do to my answer? What does moving `right` do?** (usually: one increases something, the other decreases it)
3. **What's my stopping condition?** (`left < right`, or `fast` reaches the end)
4. **Do I need to skip duplicates?** (common in Sum-family problems — check in up to 3 separate places: the outer loop, and both pointers after a match)

---

## 5. Common Mistakes

- Using two-pointer on an **unsorted** array for a sum/pair problem without sorting first.
- Letting pointers cross without checking `left < right`, causing wrong or duplicate results.
- In Sum-family problems, forgetting to skip duplicate values — causes duplicate triplets in the output.
- Calculating width/height/area **after** moving the pointer instead of **before** — this mixes values from two different pairs.
- Using a `for` loop where one of the pointers is also manually changed inside the loop body — causes that pointer to move twice per iteration. Use `while(left < right)` instead.
- Confusing two-pointer with sliding window — two-pointer indices move independently; sliding window maintains a *contiguous range* that grows/shrinks.

---

## 6. One-Minute Summary (say this out loud before an interview)

"Two-pointer uses two index variables moving through an array simultaneously instead of nested loops, bringing time complexity from O(n²) down to O(n). Opposite-ends pointers work on sorted arrays for pair-sum, palindrome, and container-style problems — you decide which pointer to move based on whether your current result is too small or too big. Same-direction fast/slow pointers handle in-place array modification. For problems needing three or more numbers, like 3Sum, you fix the extra numbers with an outer loop and sort first, then use two-pointer for the remaining two — with duplicate-skipping needed both in the outer loop and for both pointers after every match."
